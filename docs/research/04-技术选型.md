## 2. Embedding 模型

| 候选 | 版本/成绩 | 特点 |
|---|---|---|
| **Qwen3-Embedding 0.6B/4B/8B** | 2025-06 发布，8B 以 **70.58 登顶 MTEB Multilingual** | 开源可本地、32K 上下文、支持指令式检索与 MRL 降维 |
| BGE-M3 | 长期中英混合社区首选 | 稠密+稀疏+ColBERT 三模式输出、8K 上下文，与 Qdrant 稀疏检索天然契合 |
| Gemini Embedding（gemini-embedding-001 系列） | MTEB 多语榜首（API 档） | 免费额度大，但数据出境+联网依赖 |
| Jina v4 / OpenAI text-embedding-3 / Conan | 商用 API 档 | Jina v4 支持多模态图表检索，Conan 在 C-MTEB 中文榜强 |

**推荐**：**Qwen3-Embedding-0.6B 本地部署**（Sentence-Transformers/Ollama 均可，5万篇索引零成本）；若追求极致召回用 4B。**BGE-M3 作为备选**——当需要稠密+稀疏双输出喂给 Qdrant 混合检索时它更省事。
**风险**：学术文本含大量公式/符号，任何模型都需清洗；换模型需全量重建索引，起步就定好维度与归一化规范。

## 3. Reranker

| 候选 | 版本 | 评估 |
|---|---|---|
| **Qwen3-Reranker 0.6B/4B/8B** | 2025-06 与 Embedding 同套发布 | MTEB-R / **CMTEB-R**（中文重排）/ MLDR（长文档）领先；32K 上下文；8B 比小档高约 3 分 |
| BGE-reranker-v2-m3 | 开源部署量最大的 reranker | 成熟稳定、显存占用小，社区长期默认 |
| Cohere Rerank 4 | 2025-12 发布（v4.0-pro / fast） | API 档最强，100+ 语言，按量计费 |
| Jina Reranker v2/v3.5 | 商用 API | 与 Jina embedding 配套 |

**推荐**：**Qwen3-Reranker-0.6B 本地起步**（CPU 或 4GB 显存可跑），效果不够升 4B；与 Qwen3-Embedding 同源训推效果有协同。Cohere Rerank 4 仅作 API 备选（持续成本+数据出境）。BGE-v2-m3 是稳妥保守项。
**风险**：reranker 是延迟瓶颈，1万级候选务必先 hybrid 召回 top-50 再重排 top-10。

## 4. 向量数据库

| 候选 | 最新版本 | 混合检索 | 运维 | 结论 |
|---|---|---|---|---|
| **Qdrant** | v1.19.2 | **原生稀疏向量 + 内置 BM25 稀疏嵌入 + RRF 融合**；v1.19 增 TurboQuant 4bit、per-query IDF | Docker 单容器 | 5万篇≈百万级 chunk 完全够用 |
| Milvus Lite / Milvus | 2.x | 内置 BM25 稀疏稠密混合 | Lite 为 pip 库但生态重 | 超个人规模所需 |
| Chroma | 1.x（Rust 核心，4× 提速） | 1.0 起支持，但**混合检索被指云端专属**（open-core 争议） | pip 即装最简单 | 适合原型，不适合当长期底座 |
| LanceDB | 1.x | 嵌入式 FTS+向量，无服务进程 | 零运维 | Windows 单机备选，备份=拷文件 |
| pgvector | 0.8 | 需另配 BM25 | 若已用 PG 则顺带 | <500 万向量社区共识可用 |

**推荐**：**Qdrant 1.19.x（Docker Compose 一等公民）**。理由：稀疏+稠密混合检索与引用元数据过滤（按论文/章节/年份过滤）是科研问答刚需，Qdrant 是唯一三者原生齐备且运维最轻的；LanceDB 作无 Docker 时的嵌入型备选。
**风险**：个人机器重启后容器自愈需配 volume 与 healthcheck；快照 API 做每日备份。

## 5. 文档解析（重点层：学术 PDF → 结构化文本）

| 工具 | 最新版本 | 公式/表格/双栏 | 基准 | Windows 可用性 |
|---|---|---|---|---|
| **MinerU** | **4.0.12**（2026-10，安装约束 `mineru>=4.0,<5`） | PP-DocLayoutV2 布局，公式转 LaTeX，中文文献社区验证最充分 | OmniDocBench 顶级；对老旧/降质扫描件最稳 | **pip 装 CLI 有已知缺陷（issue #4433）→ 官方推荐 Docker/conda**；vllm 加速后端仅 Linux |
| Marker v2 | Datalab 2026 | olmOCR-bench **76.0 分、2.9 页/秒**，准确率与速度双第一 | 对旧降质扫描件掉到 50 分段 | pip 可用；**权重 GPL+商用限制**（商业用途需 Datalab 授权/API） |
| Docling（+Granite-Docling） | LF AI 基金会项目，2025-09 Granite 模型 | 表格/公式/阅读顺序完整，MIT 协议 | 综合略逊 Marker/MinerU | **纯 pip、Windows 最友好**，工作流集成最佳 |
| olmOCR | 持续更新 | 兼作解析器与行业基准 | — | 兜底 OCR 选项 |
| Nougat | 已停滞 | 老一代 | 被 Marker 全面取代 | 不推荐 |

**推荐**：**MinerU 4.x（经 Docker/WSL2 跑）为主力**，中文论文与复杂版式最稳且免费；**Docling 作 Windows 开发期纯 pip 的轻量通道**与 CI 回归对照；降质扫描件失败页自动 fallback 到 MinerU OCR 兜底管线。
**参考文献切分策略**：解析出的 Markdown 按 `## References` 标题定位文献区 → 逐条切分（编号/作者-年份正则）→ 建 `citation` 表（author/year/title/DOI）；正文 chunk 全部携带 `(paper_id, page, section, char_span)` 坐标，这是引用溯源准确性的地基。可选接 Grobid 精化元数据。

## 6. RAG / Agent 编排框架

| 候选 | 现状 | 评估 |
|---|---|---|
| **LangGraph 1.0** | 2025-10-22 发布首个稳定大版本 | 持久化/checkpoint、durable execution、human-in-the-loop、流式、中间件；Python 生态事实标准 |
| LlamaIndex（Workflows 1.0，2025-06 起） | 事件驱动 agentic 框架 | 检索组件最全、上手最快；深度定制后易被框架抽象绑架 |
| Haystack 2.x | 生产管线风格 | 稳但 agent/多代理生态弱于前两者 |
| 参考：gpt-researcher / STORM | gpt-researcher 在开源 deep-research 评测领先（plan→多路搜索→综合→引用报告）；STORM 走大纲驱动的维基式长文生成 | 不直接依赖，借鉴其编排模式 |

**推荐**：**LangGraph 1.x 自研轻量编排**：`规划 → 并行检索（hybrid+重排）→ 反思缺口 → 迭代补检 → 带引用综合`，对照 gpt-researcher 的 depth/breadth 参数实现"深度研究"模式；RAG 原子能力（chunking/检索/重排）自己写、不锁框架。
**风险**：LangGraph 迭代快但 1.0 已承诺 API 稳定；个人项目切忌同时引入两个编排框架。

## 7. 高级检索增强（GraphRAG 类）

| 方案 | 成本 | 适用性 |
|---|---|---|
| Microsoft GraphRAG | 最贵：单次检索约 61 万 tokens（LightRAG <100），数据更新约 $4/次且需全图重建 | 全景式主题综述有价值，个人预算不友好 |
| **LightRAG** | 建图约 $0.15/文档，支持**增量更新**，双层（实体低层/高层）检索 | 科研知识库持续增量的理想形态 |
| **HippoRAG 2**（2025-02） | Personalized PageRank，在线成本极低；多跳 QA 准确率 +20%、成本为迭代检索的 1/10~1/20、快 6-13 倍 | 性价比最优的多跳方案 |

**推荐**：V1 **不上知识图谱**——先用"Qdrant 稀疏+稠密混合 + 引用级 chunking"把地基打牢；V2 针对跨论文多跳问题（"方法 A 引用的数据集最早由谁提出"）再引入 **HippoRAG 2 或 LightRAG**，二者均可挂接现有向量库与便宜模型。
**引用溯源准确性三件套**（比任何检索花活都重要）：① chunk 带页面/章节坐标；② 生成时强制 `[n]` 编号引用且每个论断映射到 chunk id；③ 上线前用 RAGAS faithfulness 做回归门禁。

## 8. 后端 / 前端 / 评估 / 可观测

- **后端**：**FastAPI + Uvicorn**（异步、OpenAPI 自动文档、与 LangGraph 同为 Python 栈），SQLite 存书目元数据（个人规模无需 PG）。
- **前端**：自建 **Next.js + React 聊天界面**——引用卡片（点引用高亮原文 PDF 页码）是本项目核心差异化，Open WebUI/LobeChat 嵌入方案做不了这种深度定制（对比结论：Open WebUI 自带向量库最容易起 RAG、LobeChat UI 最精致，但都是"通用聊天壳"）；内部调试台用 **Streamlit** 一天搭完。
- **评估**：**RAGAS**（Context Precision/Recall、Faithfulness、Answer Relevancy 四指标 + 合成测试集，RAG 评估事实标准），可用 DeepEval 补充；TruLens 已边缘化。
- **可观测**：**Langfuse v3 self-host**（MIT 协议，核心功能免费自托管，只需承担 Postgres/ClickHouse/Minio 基础设施）；LangSmith 云版按用量计费且 self-host 锁企业版，个人项目选 Langfuse 无悬念。

## 9. 部署形态

**Docker Compose 单机栈**：`qdrant` + `mineru`（解析任务容器，按需启停）+ `fastapi` 后端 + `nextjs` 前端 + `langfuse`（含 postgres/clickhouse/minio）+ `ollama`（可选）。数据卷统一挂 `./data` 便于整体备份。
**Windows 开发注意**：① MinerU pip CLI 有坑 → 用 Docker Desktop/WSL2 跑，或开发期改用 Docling；② vLLM 无 Windows 原生支持 → 本地推理统一走 Ollama（原生 Windows），GPU 服务化留给 Linux；③ embedding/reranker 用 ONNX Runtime CPU 通道保证无卡可用；④ 路径/编码（中文文件名）统一 UTF-8。

## 成本估算（月度 API 费用量级）

- **日常问答**：20 次/天 ×（约 3 万输入 + 2 千输出 tokens，含重排后上下文）≈ ¥0.7/天 → **约 ¥20-30/月**（缓存命中率高时更低，DeepSeek 缓存命中仅 ¥0.02/M）。
- **深度研究**：每周 2 次 × 约 50 万 tokens 迭代 ≈ ¥1.5-3/次 → **约 ¥10-25/月**。
- **索引（一次性）**：解析与 embedding/rerank 全部本地零成本；1 万篇 × 8k tokens 若改用 API embedding 约 $1-2 级别，可忽略。
- **合计：约 ¥30-80/月**，无月费订阅压力；极端情况切本地 Qwen3 后 API 成本趋近于零。

## 主要风险汇总

1. **解析质量是全系统上限**：公式密集页建议抽样人工校验，建立 50 篇金标集做回归。
2. **模型迭代快**：DeepSeek 已从 V3.2→V4.1 仅用 10 个月，务必做模型路由抽象 + 定期跑 RAGAS 基线防回退。
3. **MinerU Windows 路径**：坚持 Docker/WSL2，不碰 pip CLI 与 vllm-Windows 组合。
4. **引用溯源**：依赖 chunk 坐标元数据质量，索引 schema 一次设计到位，避免重建百万级 chunk。
